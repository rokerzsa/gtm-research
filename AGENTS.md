Use ordinary sandboxed execution for this project. On 11 November 2026, a persistent Windows sandbox startup failure was repaired and verified; routine escalation is no longer needed for that issue.

If a future launch returns `helper_unknown_error: setup refresh had errors`, inspect the current dated log in `C:\Users\arifa\.codex\.sandbox` before retrying. This message describes setup before the requested command executes; changing command syntax does not resolve a setup failure. The directory belonged to `ROKERZSA\CodexSandboxOffline`, while the real user had Modify rights without permission to change its access rules.

The repair restored only `.git` directory ownership to `ROKERZSA\arifa`, using a Windows administrator prompt, preserving the existing access rules. No recursive permission reset or sandbox configuration change was needed. Record and backup: [repair report](plans/sandbox-execution-repair.md), [original descriptor](plans/sandbox-owner-before.json), [repair result](plans/sandbox-owner-repair-result.json). The repair script is retained for audit; do not run it routinely or apply it to other directories without a fresh diagnosis and appropriate authorization.

For recurrence, distinguish ownership/ACL setup errors from command errors, network errors and approval waiting. Preserve security descriptors before any targeted authorized change; verify normal sandbox startup afterward. Do not default to repeated unsandboxed executions, disable sandbox protections, or reset repository permissions broadly. File creation by a sandbox account can have different ownership from the surrounding project; the original creation history here was not established.

Execution triage for subsequent commands: start with ordinary sandbox execution. If startup fails, inspect the newest setup log and diagnose its exact failing path before retrying. If a command starts but a required network operation fails because networking is restricted, request a narrowly scoped escalated retry with its justification; do not repeat the ownership repair. For command exit errors, fix the actual command or dependency. A `hide users` / `C:\Users\Default` warning alone is not proof of startup failure: check setup `errors=[]` and the command's exit status. ## Docusaurus library architecture

- `src/pages/index.tsx` is the **site home/library index**, listing company books. It renders `research-library.json`; do not add independent hardcoded company cards.
- `research/index.md` is the **workspace index** for research projects and controls. It is not a published docs page. Update its company link/status when needed, but do not put workflow records into the public navigation.
- `research/projects/<project>/index.md` is the **operational project index**. `book/index.md` is the **reader introduction and canonical company entry page**. They serve different audiences; do not route the public home card to the operational index.
- Only `book/index.md` and Markdown under `book/part-*/` are included by `docusaurus.config.ts`. Keep registries, reviews, contracts, archives and checkpoints excluded. Do not broaden include patterns to repair a bad link.
- `research-library.json` is the single registration/order source for home cards and `sidebars.ts`. Each entry owns a unique project, sidebar ID, company label, title, description and ordered chapter tree. Keep current routes stable.
- Every company gets one company-root category linked to `book/index.md` and one **separate sidebar**. All its reading pages belong beneath that category. Next/Previous stays within the book; the first introduction has no Previous, and the final chapter has no Next. Cross-company discovery uses the home/library links, not chapter pagination.
- Do not splice `{type: 'autogenerated', dirName: '.../book'}` into a shared top-level sidebar. It emits a slice of that folder's children, not a company wrapper. `_category_.json` alone does not create the missing wrapper at the selected root. Files being on disk beneath `book/` does not prove sidebar containment.

## Adding or changing reader pages

1. Read the research project's checkpoint and preserve its evidence/review scope. Put the introduction in `book/index.md`; place chapters in a meaningful `book/part-*/` group. Do not add empty landing pages just for navigation.
2. Register the company once in `research-library.json`. Use chapter paths **relative to book, without `.md`**, retaining source prefixes in the registry. `bookDocId` follows Docusaurus's default numeric-prefix rules for each path segment, including filenames and nested folders; version-like names are preserved. Do not guess IDs from source filenames; inspect generated metadata after building. Folder names, source paths, doc IDs and browser URLs are different values.
3. List each included reader page exactly once as the introduction, chapter, linked section index or explicitly declared supplemental guide. Section objects have a label, optional substantive `index`, and ordered `chapters`. New chapters must be registered, not merely created on disk.
4. Supplemental guides are exceptional supporting routes outside sequential reading. They use sidebar `ref` items, and their frontmatter must set `displayed_sidebar` to their owning company sidebar. They must not duplicate normal reading pages or redirect pagination to another book.
5. Give new chapters meaningful `title` frontmatter and keep the introduction's reading path, section structure, manually written Next links and registered sequence consistent. Within book Markdown, use relative `.md` links to included reader pages or direct public evidence URLs. Do not link published pages to excluded operational files.
6. Keep URLs under `/docs/projects/<project>/book/`. Do not use global slugs that escape the company root. Home-page React `Link` targets omit the configured `/gtm-research/` base URL; Docusaurus adds it. Do not double-prefix paths.
7. A home card only announces the book. It is not a substitute for sidebar registration, source/claim navigation or an integrated book introduction. Existing `_category_.json` / `sidebar_position` hints do not override the registry's explicit sequence.

## Required site verification

- Run `npm run check:library` for regression tests, production build and generated navigation verification. For individual checks use `npm run test:library`, `npm run build`, then `npm run verify:library`. Run `npm run typecheck` for TS/config changes. Fix failures appropriate to the change and preserve unrelated user edits.
- The library verifier must check generated sidebar **ancestry**, actual sidebar association, every page's expected Previous/Next, terminal boundaries, included-page coverage, public home entries and excluded operational routes. A build that succeeds or a link target that exists does not prove navigation is correct.
- Check explicitly labeled Markdown Next/Previous links against the registered order as well as Docusaurus pagination. Resolve deployment paths from generated site configuration; do not hardcode a base URL into the verifier. Home-card links need company-specific accessible names.
- Keep the GitHub Pages build job running typecheck and `check:library` before site upload. Editing this validation gate does not authorize triggering a workflow, pushing, merging or deploying.
- For a new company, inspect its introduction, a middle chapter and last page in generated metadata/output. Compare its top-level sidebar and chapter sequence with the registry. Existing books must retain working roots/routes and their intended reading order.
- If browser access works, inspect the home card, company-root expansion and pagination in the UI. If it fails, state that limit; do not claim a visual pass or confuse it with a successful compiled-metadata check.
- Keep the substantive research review separate from site integration checks. Record site fixes and validation in the affected project's journal/review/dossier, then advance its checkpoint last. No publishing/deployment is implied by authoring or validation.
